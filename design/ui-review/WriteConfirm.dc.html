Landed since this review
VERIFIED now means the whole bank came back. The verdict used to be reachable after reading back 2,104 of 63,120 bytes, because the read-back lands in the same image the write was sourced from — so the untouched bytes still held what we intended and the hash agreed. The verify now requires bytes ≥ bank_len first, and a short read-back says BAD: read-back short rather than accusing the other 29.
A yes is ignored for 350 ms after arming. The app switcher is hold-A-press-encR; on the module home A alone arms and encR commits, so the two halves of the commonest navigation chord were, in order, arm and commit. One fumble put 63,120 bytes on the wire with the prompt on screen for 51 ms. The refusal inside the window is deliberately silent — a slip should feel like nothing happened.
A pre-write snapshot, and an UNDO. The bank is written to internal flash immediately before the first byte is modified. On a BAD verdict the action row is replaced by encR:UNDO encL:keep, and the restore goes back through the ordinary write machinery so the undo is itself verified. A snapshot that fails to write does not block the write — it is a net, not a precondition.
…which makes this screen's own copy stale. 29 re-sent - no undo was written when the instrument genuinely kept no copy. As of this revision it keeps one, on the same code path, a few lines above. The line and the comment explaining it both still say otherwise. Flagged rather than fixed here: the screen copy is firmware, not a design artefact.
What is already right, and should not be traded away
The changed-byte count is shown. “1 byte change” is a real check against a mistake — a number in the thousands means the wrong bank, not the wrong stage.
A nothing-to-do write is refused. Zero changed bytes blocks with “No changes to write”, rather than pushing 63,120 bytes for no reason.
Stale reads cannot be written. The bank must have come from this module, this session, at full length — a short read blocks the write outright, and the guard re-runs at commit rather than trusting the verdict from when it was armed.
Arm, then confirm — on two buttons, usually. A arms and encR commits from the module home. But reaching the same prompt through the action row’s Save entry arms it with encR too, so both halves are one button and the 350 ms window is the only thing between them. Worth closing.
The failure this is guarding against
One real read came back 957 bytes instead of 990 — one record short — while reporting success with no error. Harmless on a read. Behind a write, it would have shifted every subsequent record and rewritten twenty-nine presets that were never touched, silently. The guards exist because that has already happened once.
