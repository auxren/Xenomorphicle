ANSWERED · WHY ALL THIRTY
The bus has no per-slot data write
Not a design decision — the protocol offers no way to send data into one preset. Here is what it does offer, and the one route that might.
What the 251e actually accepts, from its own firmware
0x01 RECALL
Per-slot. Loads a stored preset into the module's live panel state. Carries no data.
0x02 SAVE
Per-slot — but it stores whatever the module currently has live, not anything we supply. We cannot put our sequence into it.
0x04 / 0x05
BACKUP / RESTORE. The only commands that move data, and they move the whole 63,120-byte bank as one continuous transfer. Not slot-addressable.
So a write is read–modify–write
read all 30
→
change 1 byte
→
write all 30 back
The other twenty-nine are rewritten with their own values, read seconds earlier — they are not erased or defaulted. So the real risk was never "we overwrite presets"; it is "our copy of them is wrong". That is exactly why the guards check freshness, the source module, and the exact byte count rather than merely asking you to confirm.
The failure that makes this concrete
One real read returned 957 bytes instead of 990 and reported success. Harmless on a read. Written back, it would have shifted every record after the truncation and quietly rewritten twenty-nine presets with mis-aligned data.
There may be a per-slot route — unexplored
Two handled commands, 0x07 and 0x08, each take a 32-bit big-endian argument and have never been investigated. If either sets a live parameter, the sequence becomes: set the live state, then 0x02 SAVE(slot) — a genuine single-slot write that never touches the other twenty-nine.
Worth knowing before betting on it: on the 259e, the equivalent parameter setters turned out to be miscompiled and dead code — they always wrote zero and were never called. The same could be true here. It needs the same firmware disassembly the rest of this was built on.
